# 技術ブログ記事を書く

このリポジトリの記事は docsify で配信される読み物である。検索から飛んできて拾い読みされる想定ではなく、通しで読まれることを前提に書く。

## 最初に読むもの

作業を始める前に、この 2 つをこの順で読む。

1. `../japanese-tech-writing/SKILL.md` — 土台の規範。論証、段落、冗長、LLM っぽい表現、翻訳調の禁止
2. `../cognitive-rhythm-writing/SKILL.md` — その上に乗せる緩急の規範

2 つは独立した選択肢ではない。後者は前者を読んでいる前提で書かれている。

`natural-japanese` は診断にだけ使う。書く工程には入れない。ビジネス文書向けの規範で、見出しの扱いがこのブログの方針と逆を向いているからである。使い方は「AI 臭さを診断する」の節にある。

## 裁定済みの判断

2 つの規範やリポジトリの設定が競合する箇所は、ここで方針を定める。

### 見出し

このブログの記事は通読される読み物であり、見出しで結論を先に渡すと読む理由が消える。
一方で「はじめに」と「おわりに」は内容を示す見出しではなく記事の枠組みを示す目印であり、読者が期待する型でもあるため、情報量のない見出しを禁じる規範より優先する。

- 見出しはオチを明かさず、その節が答える問いか扱う対象を指す
- 見出しだけ拾い読みして論旨が通る形にはしない
- 「はじめに」と「おわりに」は使ってよい
- それ以外の節には内容が分かる見出しを付ける

### 語彙

japanese-tech-writing は翻訳調の比喩と擬人化を禁じているが、名指ししているのは英語直訳に由来するものである。
文章に彩りを付けようとして当てた和語の比喩はあの網にかからないため、ここで禁じる。
判定の目安は同じで、字義どおりの動作を想像しうる述語を疑う。

- 挙動を述べる動詞は、仕様や公式ドキュメントがその挙動を何と呼んでいるかに合わせる
- 「警告が鳴る」ではなく「警告が出る」と書く
- 「将来は塞ぐ」ではなく「将来はブロックする」と書く
- 「二度目以降は黙っている」ではなく「二度目以降は表示されない」と書く
- 見出しも同じ規律で付ける（「逃し方と、逃すべきでない場所」のような凝った対比にしない）

### 文体

textlint が `no-mix-dearu-desumasu` で本文のですます統一を要求する。
cognitive-rhythm-writing の文の拍の例はである調で書かれているが、装置そのものはですます体でも成立するので、語尾だけ読み替えて使う。

- 本文はですます体で書く
- 断定は「〜でした」「〜です」と書く
- 逡巡は「〜でしょうか」「〜のはずです。ただ」と書く
- 見出しとリスト項目はですます統一の対象外なので体言止めでよい

## 記事を新しく書く

### 1. 何を書くかを固める

書き始める前に、ユーザーと次を確認する。素材が足りないまま書くと、一般論だけの記事になる。

- 読者は誰で、読み終えたあと何ができるようになるか
- 記事の核になる一つの主張は何か
- 手元にある具体（コード、計測値、実際に踏んだエラー、固有名詞）は何か

具体が出てこないときは、書き始める前にそれを言う。言い回しでは埋められない。

### 2. 骨格を置く

節の並びと、各節が答える問いを先に書き出してユーザーに見せる。この時点では本文を書かない。骨格の合意が取れてから書き始めるほうが、あとでまとめて書き直すより速い。

### 3. 書く

2 つの規範に従って本文を書く。cognitive-rhythm-writing の「執筆後の点検手順」は書き終えてから自分で回す。

コードブロックには言語を指定する。このリポジトリの docsify は Prism の bash / json / typescript / go を追加で読み込んでいる。
それ以外の言語はハイライトされないので、必要なら [docs/index.html](../../../docs/index.html) への追加をユーザーに相談する。

#### コードと出力は動かしたものを貼る

記事に載せるコード、コマンド、実行結果、バージョン番号は、`example/` で実際に動かしたものだけを書く。
想像で書いた出力はそれらしく見えるのに細部が合わず、クラス名、識別子、ファイルパス、例外の型は特に合わない。
動かさずに書いたコマンドは、動かない例になっていることがある。
動かせば、机上では出てこなかった具体が手に入る。

- 出力ブロックは実行結果から貼り、伏せるのはホスト名や絶対パスなど記事に不要な部分だけにする
- ライブラリや処理系のバージョンは、手元で動かしたものを書く
- 「〜と同じ感覚で扱える」のような、確かめていない類推を書かない
- 本文を直したら `example/` を動かし直し、コードブロックと出力ブロックを実行結果と突き合わせる

#### 表は一つの軸で組む

表の行は一つの軸だけで並べる。「方法」と「対象」のように軸が 2 つ混ざったら、片方を表に残し、もう片方は地の文で述べる。
その表の主題から外れるもの（「対象外」「別の仕組みで扱われる」）を行に混ぜない。本文で一言触れるか、落とす。

#### 初めて出す固有名には一文の言い換えを添える

方針名、機能名、規格名を初出で使うときは、その場で一文の言い換えを置く。
名前と周辺の事実を並べるだけでは、その語をすでに知っている読者にしか通じない。

### 4. ファイルを置く

```text
docs/YYYYMMDD_snake_case_slug/
├── README.md        記事本文
├── example/         記事に載せるコード（動かせる形で置く）
└── imgs/            画像があれば
```

- ディレクトリ名は公開予定日 + 内容を表す英語のスネークケース
- 本文は `README.md`
- 画像はその記事の `imgs/` に置く
- 記事にコードを載せるなら、その記事の `example/` に動かせる形で置く（ビルド定義と、全部を順に実行する手段を添える）
- 図は drawio の `.drawio.svg` 形式にして、VS Code 上で編集できる形を保つ
- 記事を追加したら `docs/_sidebar.md` に `- [タイトル](./ディレクトリ名/README.md)` を一行足す
- サイドバーの並びは新しい記事が下に来るよう追記する

### 5. 検査する

書き終えたら 2 つの検査をかける。どちらの指摘も、次の「指摘の仕分け」に従って扱う。

```bash
npx textlint "docs/**/*.md"
npx markdownlint-cli2
```

続けて AI 臭さを診断する。

## 既存記事を直す

推敲を頼まれたときは、いきなり書き換えない。
まず対象を読み、2 つの規範に照らして問題の箇所と理由を挙げ、どこまで手を入れるかをユーザーと決める。

全面リライトと部分修正では結果が大きく変わる。
cognitive-rhythm-writing の「修正指示への使い方」に症状から処方を引く表があるので、診断にはそれを使う。

書き換えたあとは新規執筆と同じく lint を通す。

## AI 臭さを診断する

textlint は文単位の表層しか見ない。
文頭の言い回しが何回反復しているか、対比構文が全体の何%を占めるか、語彙がどれだけ使い回されているかという文書全体の統計は測れない。
統計は書いた本人（人でも LLM でも）が読み返しても気づけない層なので、機械に測らせる。

`natural-japanese` スキルを診断モードで呼ぶ。lint スクリプトを直接叩かない。スコアの算出式も出力形式も向こうが持っているので、委譲したほうが上流の更新に追従できる。

```text
/natural-japanese score quick <記事のパス>
```

ジャンルは tech として扱ってほしい、と併せて伝える。
診断は推敲フェーズの入口で一度でよい。統計系の検出器は文書全体を見るため、書きかけでは意味のある数字が出ない。

返ってくるスコアは合否ではない。使うのは「理由トップ3〜5」のほうで、それを次節の仕分けにかける。
診断で終わりにしない。仕分けて「直す」になったものは、`japanese-tech-writing` と `cognitive-rhythm-writing` に照らして実際に書き直すところまでやる。そのうえで直した結果をユーザーに見せる。

書き換えを `natural-japanese` にやらせないことだけ守る。
`natural-japanese` の工程は文体憲法12条に沿って直すので、見出しに結論を埋め込む、箇条書きを地の文に戻すといった、このブログの方針と逆を向いた修正が混ざる。
診断モードが頼まれるまで直さないと自ら定めているのは好都合なので、その境界をそのまま使う。測るのは `natural-japanese`、直すのは規範という分担である。

直したら診断をもう一度かける。統計系の指摘は一箇所を直すと別の箇所の比率が動くので、解消したか、別の finding を生んでいないかを見る。
新しい finding が出なければ収束とみなして止めてよい。同じ finding が二周続けて残るなら、その finding は直すべきものではない可能性が高い。理由を書いて残すか、ユーザーに相談する。

## 指摘の仕分け

textlint も markdownlint も診断も、設定や閾値は完成品ではない。
記事を書きながら見直す前提のものなので、指摘が出たときに文章を機械的にツールへ合わせにいかない。
指摘は次の 2 つに仕分ける。

### そのまま直す

文章の狙いと関係なく直せる指摘は、断りなく直してよい。

- 表記ゆれ（prh）
- 括弧まわりの空白
- 二重否定
- 冗長表現

### 相談する

規範が意図的にやらせていることを lint や診断が咎めている場合は、ユーザーに判断を仰ぐ。
ルールを緩めるほうが正しい場面はあり、`max-ten` と `no-doubled-joshi` は実際にそうやって調整した。
判断はユーザーのものなので、勝手にどちらへも倒さない。

示すのは次の 3 点。

1. どのルールが本文のどこを指しているか
2. その書き方を選んだ理由（どちらの規範の、どの装置か）
3. 文章を直す・ルールを緩める・この箇所だけ除外する、のどれを取るか

ぶつかりやすい組み合わせは分かっている。

| ルール                                       | ぶつかる装置                                             |
| -------------------------------------------- | -------------------------------------------------------- |
| `@textlint-ja/preset-ai-writing`             | 逡巡（「〜でしょうか」）と繰り返しによる強調             |
| `ja-technical-writing/max-ten`               | 「立てる、流す、止める」の流す文                         |
| `ja-technical-writing/sentence-length`       | 「立てる、流す、止める」の流す文                         |
| `ja-technical-writing/no-mix-dearu-desumasu` | 見出しやリストの体言止め（本来は対象外だが誤検出しうる） |

## 終わったと言う前に

- textlint と markdownlint が両方通っている
- AI 臭さの診断をかけ、指摘を仕分けた（残したものは理由を言える）
- cognitive-rhythm-writing の「執筆後の点検手順」を回した
- 相談すべき lint 指摘を握りつぶしていない
- `example/` を動かし、記事のコードブロックと出力ブロックが実行結果と一致している
- 具体（コード、数値、実例）が入っていて、抜くと成立しない段落がある

最後の一つが満たせないときは、記事ができたと言わない。何が足りないかを伝える。
